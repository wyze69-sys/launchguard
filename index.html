A mint is the token's own address on Solana — not a wallet address.

Technical details

The network menu picks which Solana network the mint is looked up on. Most real tokens are on mainnet-beta; devnet is a test network.

This page reads from free public Solana endpoints. Those endpoints limit how often you can ask (they answer HTTP 429 when you ask too much), so a check can fail at busy times. For anything beyond a quick look, add your own keyed endpoint (Helius) using the LAUNCHGUARD_CONFIG note at the bottom of this file.

Verify a report

Paste a report or memo text. We recompute its fingerprint (SHA-256) — a code that changes if anyone edits the report — and compare it with the report, so you can tell if it was changed.

If they don't match, don't trust that memo.

Technical details

You can paste report JSON (from a report's "Copy report JSON" button) or a memo text carrying an h= digest.

Report JSON is verified by recomputing its SHA-256 digest from the canonical form. Memo text is compared against the digest of the report currently shown on the Check screen, and its mint/score/band fields are cross-checked against that report.

One outcome to know in advance: FIELD MISMATCH means the memo's digest matches the displayed report but its printed mint/score/band fields disagree with it — in plain words, the memo text and the report do not describe the same result, so do not trust that memo for this report.

How it works

Paste a token's mint address on the Check screen. LaunchGuard reads the token's live facts from the Solana blockchain and scores its risk from 0 to 100. Every warning in the report is explained in plain words, next to the facts it came from.

When a report is finished, you can save it on Solana devnet as a short memo note — a public record of what the report said, about which token, and when. Anyone can then use the Verify screen to check the report was not changed after it was written: it recomputes the report's fingerprint (SHA-256), a code that changes if anyone edits the report.

What we check — and what we don't check

What we check:

  • Who can create more of this token — and whether that power has been given up
  • Who can freeze the token, so holders cannot move it
  • How much of the token the biggest holders own
  • The total supply
  • Special Token-2022 features, in plain words — for example a fee taken on every transfer, or transfers that can be paused
  • Whether the token trades on exchanges we know

What we don't check:

  • Whether the pool tokens are locked or burned
  • Whether several holder accounts secretly belong to one owner
  • The history of whoever created the token

Every report also carries its own list of what was checked and what was not, in plain language, right under the score.

Technical details
  • Liquidity is checked on these venues: Raydium AMM v4, Meteora DLMM, Meteora DAMM v2, Meteora DAMM v1 and Orca Whirlpool. Whether LP tokens are locked or burned (LP burn / lock status) is "not-checked" — a pool existing cannot by itself prove tokens are locked or burned.
  • Holder count is a floor derived from the largest-accounts call, not a full indexer count. Counts are of token accounts, not owners: one owner can hold many accounts.
  • Liquidity detection covers the venues named above — a mint trading solely on another venue reads as "not detected", which is why that signal is a 0-point informational flag and never proof of anything.
  • If a Token-2022 account comes back unparsed, the extension set is honestly recorded as unknown; an extension the tool does not recognise is named in the report's data-confidence reasons as incomplete coverage.
  • Wallet discovery for anchoring is implemented, in priority order: Wallet Standard first, then the legacy injected provider (window.solana), then the namespaced window.phantom.solana provider.
  • A memo anchor proves what was said and when — not that the score was correct. Scoring is heuristic: a clean score is not a safety guarantee.
  • Public RPC endpoints rate-limit (HTTP 429). The data layer backs off twice and then fails with a specific message; use a keyed endpoint (Helius) for anything beyond a quick look.

How scoring works

The score runs from 0 to 100 — higher means riskier.

  • 0–29 · LOWER OBSERVED RISK — few warning signs were seen
  • 30–59 · CAUTION — some warning signs were seen
  • 60–100 · HIGH RISK — serious warning signs were seen

The lowest band is called LOWER OBSERVED RISK because the score only reports what was seen on the blockchain. It is not a promise that a token is safe.

Every warning flag is shown in the report with its points and a plain-words explanation, and the report shows the exact facts table the score came from. If a fact could not be read, it never adds points: the gap is shown in the report's data-confidence note instead.

LaunchGuard is an informational screening tool, not financial advice.
